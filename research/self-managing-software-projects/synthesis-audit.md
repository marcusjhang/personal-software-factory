# Synthesis audit: self-managing software projects

**Scope.** This memo audits the 14 validated result files against `outline.yaml` and `fields.yaml` as of the stated research cutoff (2026-09-13). It cross-checks repeated claims rather than treating repetition across files as independent corroboration. Many files reuse the same SWE-bench, METR, DORA, AgentDojo, and vendor sources.

## Robust conclusions

### What is actually solved

1. **The deterministic control plane is mature.** Issue templates, branch isolation, CI checks, protected branches, merge queues, environment approvals, artifact attestations, rollback, durable queues, retries, and audit logs are normal production engineering. Agents can be inserted as untrusted workers that check out a repository, edit, test, and return a branch or draft PR. GitHub's own design limits its cloud agent to a bounded branch/PR flow and keeps merge human-controlled ([GitHub risks and mitigations](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/risks-and-mitigations)).
2. **Routine dependency maintenance is the strongest autonomous use case.** Discovery, advisory matching, lockfile updates, grouped PRs, and narrowly allowlisted auto-merge after independent CI are established. Even here, support is strongest for patch/minor or development dependencies with good tests, supplier policy, soak time, and rollback. It does not extend to major migrations or proof that a package is benign. An empirical study found 65.42% acceptance of Dependabot security PRs, but acceptance is not correctness ([MSR 2021](https://doi.org/10.1109/MSR52588.2021.00037)).
3. **Bounded issue-to-draft-PR work is real and useful under supervision.** The repeatable unit is a clear, single-repository, low/medium-risk task with a reproducible environment and an independent acceptance oracle. This includes routine tests, docs, lint fixes, small bugs, and some migrations. Product intent, architecture, security-sensitive work, merge, and deploy remain outside the reliable agent boundary.
4. **Deterministic remediation is mature; novel AI remediation is not.** Desired-state reconciliation, restarts, scale actions, traffic shifting, canary aborts, rollback, and pre-vetted runbooks can safely close loops when preconditions, blast radius, and reversal are explicit. AI diagnosis and patch proposals can shorten triage, but the evidence does not support an agent inventing and deploying a novel production repair without approval. ITBench's best reported GPT-4o results were only 13.81% diagnosis and 11.43% mitigation pass@1, with 0% on hard repair ([ITBench](https://arxiv.org/abs/2502.05352)).
5. **Quality-gate enforcement is solved; complete semantic oracles are not.** Tests, lint, type checks, SAST/SCA, fuzzing, policy checks, and provenance reliably enforce the evidence they encode. They cannot establish that the specification is right, hidden behavior is preserved, an agent-written test is independent, or a package/source change is non-malicious. AI review is a useful extra signal, not an independent approval authority.
6. **Durable orchestration is production-ready, but multi-agent superiority is unproved.** Temporal-style history, queues, idempotent activities, leases, retries, checkpoints, budgets, and human interrupts are suitable control-plane components. Multiple agents can add parallel search or independent review where outputs have objective scoring. Conversational agent hierarchies also add coordination failure, correlated error, cost, and state inconsistency; the MAST study identifies 14 recurring failure modes across seven frameworks ([MAST](https://arxiv.org/abs/2503.13657)).

### What is conditionally useful

- Event/schedule-driven triage, issue decomposition, coding, CI-failure diagnosis, test generation, AI review, security-fix drafts, and low-risk auto-merge are useful only with task-class allowlists, hard budgets, reproducible environments, independent checks, and a named owner.
- Spec frameworks can improve the handoff by making acceptance criteria and non-goals explicit, but no independent controlled evidence shows that Spec Kit, Kiro, OpenSpec, or similar frameworks outperform disciplined issue templates and reviews.
- Self-hosted open-source workers improve control and portability only for organizations able to operate secure ephemeral compute, secrets brokerage, policy, observability, and upgrades. “Open source” does not imply turnkey governance or zero commercial dependencies.
- Feedback loops are safe when production failures become reviewed, versioned eval cases and changes pass shadow/canary/rollback gates. Graders, policies, permissions, and their training data must remain independently governed.

### What remains experimental or unsupported

- Unattended product discovery, priority setting, ambiguous requirements resolution, architecture ownership, cross-repository change coordination, production deployment, novel incident repair, and recursive policy/tool self-modification.
- A single closed loop that repeatedly plans, builds, merges, deploys, observes, repairs, and learns with a denominator-based safety, reliability, and cost record. The end-to-end architecture results explicitly found no such evidence.
- Robust prompt-injection prevention for agents consuming issues, repository files, logs, web pages, dependencies, or MCP outputs while holding consequential tools. OWASP states that fool-proof prevention is unclear ([OWASP prompt injection](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)).

## Disputed/weak claims

- **“Autonomous software engineer” is broader than the evidence.** Product docs establish autonomous execution inside a task, not autonomous accountability for requirements, correctness, merge, deployment, or operations.
- **Merge rate and PR volume do not establish productivity.** Cognition reports a 67% Devin PR merge rate and large volume, but omits a complete assigned-task denominator, reviewer/rework cost, latent defects, and a human counterfactual ([Cognition](https://cognition.com/blog/devin-annual-performance-review-2025)). The independent Answer.AI trial saw only 3 successes in 20 tasks ([Answer.AI](https://www.answer.ai/posts/2025-01-08-devin.html)); it is small and old, but blocks any universal reliability claim.
- **Enterprise case studies are existence evidence, not general effect estimates.** Claims such as 30–79% faster delivery, large hours saved, or very high “accuracy” are selected first-party/customer reports with incomplete denominators and attribution. They can show feasibility in a prepared environment, not transferable ROI.
- **Static benchmark gains are not production SLAs.** Scores change with model, scaffold, token budget, test subset, issue vintage, and training exposure. SWE-Bench+ reduced one reported 12.47% result to 3.97% after leakage/weak-test filtering ([SWE-Bench+](https://arxiv.org/abs/2410.06992)); SWE-bench-Live reported 43.20% on Verified versus 19.25% on fresh Live issues in one matched setup ([SWE-bench-Live](https://arxiv.org/abs/2505.23419)). These findings do not prove all static results are contaminated, but they rule out naive transfer.
- **Current productivity magnitude is unresolved.** METR's early-2025 randomized study found experienced maintainers 19% slower ([METR early study](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). Its later raw estimates point toward 18% and 4% speedups, but confidence intervals cross zero and the authors call the evidence very weak because of selection and concurrency measurement ([METR update](https://metr.org/blog/2026-02-24-uplift-update/)).
- **AI review is not a substitute for human review.** In one small professional study, reviewers retained 89% of AI-surfaced issues, yet the system surfaced only 42% of injected issues and did not save time ([review study](https://arxiv.org/abs/2411.11401)). Use it for candidate finding, not approval.
- **Vendor “RCA accuracy” is not comparable to adversarial incident repair.** Sentry reports 94.5% RCA accuracy over 38,000+ issues, but does not publish sampling, labels, exclusions, confidence intervals, or deployment outcomes ([Sentry](https://blog.sentry.io/seer-sentrys-ai-debugger-is-generally-available/)). It cannot be reconciled numerically with ITBench without a common protocol.
- **More agents are not inherently better.** Agentless reported 32% on SWE-bench Lite at $0.70 using a simpler fixed pipeline ([Agentless](https://arxiv.org/abs/2407.01489)). Multi-agent papers show some gains, but mostly in benchmark/preprint settings; routing and verification, not agent count, may explain the gain.
- **GA, preview status, stars, and feature lists measure availability, not efficacy.** They must not be used as evidence of unattended lifecycle reliability.

## Cross-item conflicts

1. **Vendor deployment success versus independent field evidence.** Devin/customer volume and merge claims conflict with Answer.AI and early METR. Task selection, product generation, enablement, outcome definitions, and publication bias explain much of the gap. Report them side by side; do not average them.
2. **Short-task acceleration versus whole-system delivery.** GitHub's constrained-task speedup can coexist with DORA's worse throughput/stability associations. More code can enlarge batches and increase review, integration, and operational load; DORA also cannot establish causality.
3. **Leaderboard progress versus audit/freshness results.** Real model and harness progress can coexist with leakage, weak tests, and stale task exposure. Pin dataset, split, harness, model, date, and budget. Prefer recent private issues with independent hidden checks.
4. **Sentry's 94.5% RCA versus ITBench's 13.81%.** The former is an opaque vendor operational metric; the latter is a reproducible but synthetic Kubernetes challenge. They measure different labels and difficulty. Neither is a universal production rate.
5. **Low dependency build-breakage versus warnings that autofix may be insecure.** Dependency-version PRs, source-code security patches, and malicious upstream releases are distinct. Green builds support narrow update automation but cannot certify semantic compatibility or supplier trust.
6. **Automation consistency versus automation-amplified incidents.** Reconciliation and runbooks reduce toil, yet automated actuation replicates a wrong rule rapidly. This is not a reason to reject automation; it is a reason to require monotonic/convergent actions, blast-radius caps, canaries, circuit breakers, and rollback.
7. **Human review required versus human review sufficient.** Vendors correctly retain human merge gates, but reviewers can anchor on plausible output or rubber-stamp high-volume diffs. Qualified code owners, review-size limits, deterministic evidence, and separation of duties are required.
8. **Provenance versus safety.** SLSA, in-toto, and Sigstore can prove how/where an artifact was built; they do not prove agent-authored source is correct or benign ([SLSA verification](https://slsa.dev/spec/v1.2/verifying-artifacts)).

## Missing caveats

- Repeated citation across the 14 items is often the **same evidence**, not 14 confirmations. The final report should label reused cornerstone studies.
- “Success,” “accepted,” “merged,” “passed,” “resolved,” “RCA accuracy,” and “hours saved” use different denominators. Never compare them without an explicit outcome definition and funnel from assigned task to durable production result.
- Public benchmarks omit review time, retries, CI cost, deployment, escaped defects, rollback, maintainability, and incidents. They also age quickly and may have training exposure.
- Security benchmark attack-success rates are adversarial stress tests, not production incident base rates. Conversely, absence of public incidents is not evidence of safety.
- An ephemeral container limits persistence but does not prevent in-run token theft, network exfiltration, malicious dependency scripts, privileged runner escape, cache poisoning, or cross-boundary MCP misuse. The `tj-actions/changed-files` compromise showed secrets can be stolen during a run ([Unit 42](https://unit42.paloaltonetworks.com/github-actions-supply-chain-attack/)).
- Least privilege must be enforced outside the model. Separate untrusted reading/triage from write-capable execution. Broker short-lived credentials. Disallow the worker from changing branch protection, its policy, its evaluators, or deploy credentials.
- CI written by the same agent is not independent evidence. Agent-authored workflow changes need separate approval, and untrusted PR code must not run in privileged `pull_request_target` contexts ([GitHub Security Lab](https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/)).
- At-least-once queues and retries can duplicate branches, comments, releases, or rollbacks. Every external mutation needs idempotency, reconciliation, and an append-only audit record. “Exactly once workflow” does not imply exactly-once external side effects.
- Auto-merge thresholds cannot be borrowed from a vendor or public benchmark. They require local risk-tiered samples, confidence intervals, reviewer time, reverts, escaped defects, and rollback tests.
- Build-versus-buy comparisons must include platform engineering, sandbox and runner cost, secrets and policy work, review/rework, vendor/model drift, data residency, retention, audit export, and exit cost—not seat or token price alone.
- Item 05 records a live-documentation conflict over whether Dependabot security-update PRs are uncapped or subject to a limit of 10. Verify behavior in the target repository before making capacity assumptions.
- Item 13 reports that Serper search was unavailable. Therefore “no validated example was found” is supportable, while “no example exists” is not. Private deployments are also systematically underrepresented.
- Product limits, prices, defaults, and GA/Preview labels are mutable. Revalidate them at procurement or publication time and pin exact model, product, and framework versions.

## Final-report recommendations

1. **Lead with a three-tier maturity verdict.** Solved: deterministic control plane and narrow maintenance. Conditionally useful: supervised issue-to-PR, test/review assistance, and vetted remediation. Experimental: autonomous product/architecture/deploy/novel repair/self-governance.
2. **Define “self-managing” as governed bounded autonomy, not minimal clicks.** The target architecture should treat agents as replaceable, untrusted workers beneath a deterministic policy and workflow layer.
3. **Recommend staged adoption by task class.** Start with dependency/dev-tool updates, docs/tests/lint, and draft PRs. Require READY criteria, one owner, time/token/tool budgets, isolated execution, independent CI, small diffs, human merge, canary, rollback, and post-deploy observation. Expand only on local evidence.
4. **Keep hard separation of duties.** The proposing/coding agent must not approve itself, author its own authoritative tests/policy, change branch protection, or hold production credentials. Sensitive paths always require qualified human/code-owner approval.
5. **Use deterministic security boundaries.** Treat issues, repository text, logs, webpages, dependencies, and MCP output as hostile. Use network deny-by-default/allowlists, registry allowlists, short-lived scoped credentials, separate trust zones, immutable policy from the default branch, signed provenance, and full audit/kill-switch support.
6. **Measure the whole outcome funnel.** Report assigned tasks, clarified/rejected/aborted runs, accepted without material edit, reviewer minutes, retries, CI/inference cost, lead time, reverts, escaped defects, incidents, and durable post-deploy success. Compare against a no-agent or simpler-pipeline baseline.
7. **Use fresh private evals and repeated stochastic trials.** Pin model, scaffold, prompt, tools, budget, repository SHA, and dataset date. Include negative/adversarial tests and report confidence intervals. Do not promote on public leaderboard score or self-reported confidence.
8. **Prefer the simplest adequate topology.** Use a fixed pipeline or single worker before adding multi-agent routing. Add parallel agents only when work is independent and outputs can be objectively compared; prove marginal quality after extra cost and coordination failures.
9. **Keep learning governed.** Production traces may propose evals, prompts, runbooks, or policy changes, but humans must curate labels and approve evaluator, permission, and policy changes. Never train directly on raw user feedback or let an agent weaken its own gates.
10. **State the decisive evidence gap plainly.** No reviewed source establishes a denominator-based, independently audited rate or ROI for autonomous plan→production→observe→repair→learn operation. The recommended system is therefore a well-governed automation platform with agent workers, not an autonomous software organization.
